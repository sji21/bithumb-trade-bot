## Critical — 지금 구조의 핵심 문제

### 1. 문서상 “본전략”과 실행 경로가 다르다

문서:
- 본전략 = **일봉 3신호 비중**
- 동작 = **알림 전용, 주문 수동**
- 4시간봉 = 시세 확인용

코드 현실:
- `daily_report()` → 일봉 3신호 **계산·알림만**
- `process_asset()` → 여전히 **4h EMA 크로스 신호 + 주문 경로**
- `backtest.py` → 여전히 **EMA 크로스만** 검증

즉:
- 채택 전략은 **리포트 레이어**
- 폐기한 전략이 **실행·백테스트 레이어**에 남아 있음

`ENABLE_LIVE_TRADING=true` 되는 순간, 문서의 3신호 비중이 아니라 **옛 EMA 바이너리 매매**가 나간다.
가장 위험한 불일치다.

### 2. `REBAL_BAND`가 설정만 있고 안 쓰인다

- `config.REBAL_BAND = 0.10`
- 문서: 목표-현재 차이 10%p 미만이면 거래 안 함
- 코드: **참조 없음**

`report.build_daily()`는
- 비중 숫자 변화 → “조정 필요”
- 금액 gap → `MIN_ORDER_KRW`만 비교

**10%p 밴드는 구현되지 않았다.**

### 3. 채택 전략 백테스트 엔트리가 없다

README:
> 봇이 실제로 쓰는 strategy 모듈을 그대로 불러 쓴다

맞긴 한데, `backtest.py`가 부르는 건 `analyze()` / EMA 신호다.
`analyze_daily()` 기반 포트 시뮬레이션이 없다.

결과적으로:
- 문서의 876% / MDD -38% 숫자는 **이 레포 실행 파일로 재현되지 않음**
  - 2026-08-06 후속: 재현 엔트리(`--portfolio`)를 만들자 **SOL 오염**으로 판명.
    실제 BTC70/ETH30 은 541% / MDD -40%. docs 정정 완료
- 회귀 테스트 수단이 없음

### 4. 주문 실패해도 캔들을 “처리 완료”로 찍는다


### 5. 일봉 리포트: 본문 성공 후 차트 실패를 재시도하지 않음

```python

for ... send_photo(...)
sent_dates['daily'] = today
```

텍스트만 가고 차트 일부가 실패해도 그날 완료 처리.
차트 재전송 없음.

### 6. 워밍업 부족 신호가 조용히 False/삭제된다 (정정)

초기 지적:
```python
'fast': bool(ds.sig_fast.iloc[-1]),
```
`bool(nan) is True` 경로를 우려했으나, **실제로는 `iloc[-1]`에 NaN이 오지 않는 경로**다.

런타임 검증 (2026-08-06):
- `shift(1)` NaN은 index 0 근처
- 워밍업 구간의 `ma_fast > ma_mid` 비교는 NaN이 아니라 **False**
- n=2/60/100/205/480 모두 마지막 봉 `sig_*` 에 NaN 없음

**진짜 버그:** "계산 불가"가 "신호 꺼짐"으로 조용히 붙음.

| 봉 수 | MA200 | score | weight | 의미 |
|---|---|---|---|---|
| 60 | 계산 불가 | 0.35 | 0% | 전량 현금처럼 보이지만 데이터 부족 |
| 100 | 계산 불가 | 0.80 | 80% | 신호 1개가 빠졌는데 경고 없이 그럴듯한 숫자 |
| 205+ | 정상 | 1.00 | 100% | 정상 |

현재 `DAILY_HISTORY_DAYS=480`이라 평소 안 터지지만, 응답이 짧아지거나 신규 상장 종목이면 바로 발생.
수정 방향: NaN `bool` 방어가 아니라 **워밍업 미달 시 명시적 실패/리포트 보류**.

### 9. 백테스트 `HOLD_THRESHOLD_KRW` 단위 버그 → **재정정: 영향 없음**

> 이 항목은 두 번 틀렸다. 원본은 “왜곡된다”로 뭉갰고, 1차 정정은 반대로 P0까지
> 올렸다. 실행해서 확인한 결론은 **버그는 맞지만 동작은 바뀌지 않는다**이다.

`HOLD_THRESHOLD_KRW=10000`을 USD 시뮬레이션 `coin * price`와 비교한다.

- 의도: ₩10,000 → 약 $7 이상이면 전액 투입
- 실제: **$10,000** → 약 ₩1,390만 이상이어야 전액 투입
- 배율: 약 **1,390배**

여기까지는 사실이다. 그런데 **분기가 갈리지 않는다.**

`_order_for_sell` 이 전량 청산(`volume = coin * USABLE_RATIO`)이라 매도 직후
보유량은 0이 된다. EMA 크로스는 매수·매도가 교대로 나오므로 **매수 시점의
`coin` 은 항상 0** 이고, `coin_krw >= ₩10,000` 조건은 실제 봇에서도 참이 되지
않는다. 임계값을 어느 단위로 두든 `budget = 현금 × 0.5` 분기만 탄다.

런타임 검증 (2026-08-06, 실데이터 180일, 양쪽 규칙 동시 계산):

| | 매수 | 연속 매수 | 전액투입 발동 (USD 기준) | 전액투입 발동 (KRW 기준) |
|---|---|---|---|---|
| BTC | 41회 | **0회** | 0회 | **0회** |
| ETH | 44회 | **0회** | 0회 | **0회** |

따라서 README/research-log 의 **“EMA 크로스 (봇 = 50%) -12.7%” 는 실제 봇
동작과 일치하며, 라벨도 정확하다.** publish된 숫자에 문제 없음.

남는 것은 코드 위생 문제뿐이다 — KRW 이름의 상수를 USD 값과 비교하고 있어
다음 사람이 오해한다. 진입 규칙을 바꾸거나 분할 매수를 도입하면 그때는 실제로
갈린다. **P0 → P2.**

## 모듈별 짧은 코멘트

- **`config.py`**: 경로 절대화·모드 라벨 좋음. 안 쓰는 실행 파라미터와 본전략 파라미터가 공존.
- **`strategy.py`**: 일봉 쪽은 깔끔. EMA 쪽은 레거시. 워밍업 미달을 False로 조용히 삼키는 부분 수정 필요.
- **`bithumb.py`**: 실전 교훈이 잘 반영된 베스트 모듈.
- **`state.py`**: 설계 의도가 주석과 구현 모두 좋음.
- **`bot.py`**: 오케스트레이션은 단순. 이중 전략이 문제의 중심.
- **`report.py`**: 가독성 좋음. 밴드/포트 규칙 부족.
- **`charting.py`**: 일봉 5단 차트는 운영 가치 큼.
- **`backtest.py`**: 현재 본전략 기준으로는 만료.
- **`docs/*`**: 이 레포의 진짜 자산. 특히 실패 기록과 검산 규칙.
